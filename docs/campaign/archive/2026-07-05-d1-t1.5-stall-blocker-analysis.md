**Resolved by hardening phase H4 (2026-07-05).** Fix direction 1 below was
implemented: the fast-path pre-pass now dispatches to the worker thread via
a new `fastPathRequested`/`fastPathReady` command-channel signal pair
instead of running synchronously on the caller's thread. See
`2026-07-05-sync-hardening-phases.md` §7 and FINDINGS.md O16 for the landed
design and `SyncEngineWorker::prepareFastPath` in `syncengine.cpp` for the
implementation. Kept below for its still-accurate root-cause analysis and

## 2. Campaign context (read this if you're new to D1)

### 2.1 The parent problem

PlanStan (a calendar app) synchronizes against CalDAV servers and local
directories via libkalburator's sync engine. A real-world Nextcloud account
hit a bug where a local-mirror collection **soft-froze every 120 seconds**
because sync could never converge — corrupted recurrence data, a
non-converging diff, and a silent-empty-read risk combined to produce an
unresponsive GUI. That investigation is written up in PlanStan's
`docs/bugs/sync-nonconvergence-vtimezone-corruption-and-dav-transport.md`
(findings N1–N9) and tracked end-to-end in libkalburator's
`docs/campaign/2026-07-03-sync-convergence-roadmap.md`.

Tracks A (canon correctness), B (sync-stack integrity/convergence), and C
(PlanStan-side integration) from that roadmap are **complete**. The
convergence bug itself is fixed. What remains from that investigation is
finding **N7**: the actual mechanism of the 120-second freeze is that
**CalDAV network I/O and LocalBackend's full-directory filesystem scan run on
the GUI thread**. The sync engine's own worker (`SyncEngineWorker`, on its own
`m_workerThread` — see §3 below) calls into backend objects via
`QMetaObject::invokeMethod(backend, ..., Qt::BlockingQueuedConnection)`. Pre-D1,
those backend objects (`LocalBackend`, `RemoteCalendarBackend`) live on
**the GUI thread**, so every one of those calls blocks the GUI thread for as
long as the backend method takes — which, for a large mailbox transferring
hundreds of items over a slow or lossy connection, is enough to visibly and
completely freeze the application for up to 120 seconds.

### 2.2 The fix: D1

**D1** ("DAV I/O off the GUI thread") is the architectural fix: move
`LocalBackend` and `RemoteCalendarBackend` instances off the GUI thread onto
a **dedicated I/O `QThread`**, so those `BlockingQueuedConnection` calls from
the engine's worker thread land on the I/O thread instead of the GUI thread.
The GUI thread is then free to keep processing paint events, user input, and
timers throughout the entire sync, no matter how slow the network or how
large the mailbox.

The full plan for this — four stages, PlanStan-side adoption included — is
`docs/campaign/2026-07-04-d1-threading-execution-plan.md` (hereafter "the D1
plan" or "the execution plan"). It was itself the product of **"a 2026-07-04
cross-repo viability audit"** (referenced in the plan's §0) that concluded D1
was safe to attempt because every code path the engine uses to reach a
backend already goes through `QMetaObject::invokeMethod(...,
Qt::BlockingQueuedConnection)`, resolved dynamically against the backend's
*actual* thread at call time — so moving a backend's thread affinity was
claimed to "automatically retarget every call site" with **"no engine changes
expected in D1."**

That claim turned out to be almost, but not quite, true. This document is
about the "not quite."

### 2.3 Why threading has failed before (read this before proposing any fix)

The execution plan's §0 is explicit that two prior attempts at streaming sync
progress (January 2025) failed and were reverted, and their postmortems
(`PlanStan/docs/complete/postmortem_sync_progress_attempt{,_2}_2025_01.md`)
codified hard rules that bind all future threading work in this codebase:

> **no `processEvents()`, ever** — if you feel the need, the architecture is
> wrong; feature branch + commit per increment.

Any fix proposed for the finding in this document **must not** introduce
`processEvents()`, a new nested event loop on the GUI thread, a mutex around
a backend, or a `sleep`. The execution plan's §7 (Abort/fallback ladder)
calls these out explicitly as "the failure signature of attempts 1 and 2."

### 2.4 Prior building blocks this session relied on

Two already-landed pieces of infrastructure made D1 viable at all (per the
plan's §0):

- **v0.72 `onOwnerThread` fix** (`434c7d4`) — made the sync-operation API
  (`FetchOperation`/`PushOperation`/`DeleteOperation`) thread-relocatable: an
  operation object constructed from a worker thread still ends up owned by
  the *backend's* thread, not the calling thread.
- **`6579dfb`** — made `GenericSqliteBackend` thread-safe via per-thread
  connections.

### 3.1 T1.1 — shared, lazily-created `QNetworkAccessManager`

`RemoteCalendarBackend`'s internal `davSyncRequest()` free function
(`src/calendar/remotecalendarbackend.cpp`) used to construct a **fresh**
`QNetworkAccessManager` on every single call — a fresh TCP+TLS handshake per
request. Fixed: added a `QNetworkAccessManager *m_nam` member, lazily created
on first use via a new `nam()` accessor. Lazy creation matters for D1
specifically: it means the QNAM acquires the thread affinity of *whichever
thread first issues a DAV request* — which, if the backend is moved to the
I/O thread *before* first use (the D1 relocation pattern), is the I/O thread,
not the construction thread. Also added
`Q_ASSERT(QThread::currentThread() == nam->thread())` at `davSyncRequest`'s
entry, turning a future affinity regression into a loud debug-build crash
instead of a silent race.

Full suite green (158/158) after this change.

### 3.2 T1.2 / T1.3 — lazy-open `CTagStore` and `FingerprintStore`

Both `RemoteCalendarBackend`'s private `CTagStore` and `LocalBackend`'s
private `FingerprintStore` (both SQLite-backed) used to open their
`QSqlDatabase` connection **eagerly in their constructor**, which runs inside
`setDbPath()`. Whoever calls `setDbPath()` — historically always the same
thread that would go on to use the store — permanently owns that SQL
connection's thread affinity, because **Qt's SQL module ties a named
connection to the thread that opened it**; using it from another thread
produces the (very real, seen firsthand in this session — see §4.4 below)
warning `QSqlDatabasePrivate::database: requested database does not belong to
the calling thread`.

Fixed identically for both stores (mirroring the existing
`CalDavContentCache` lazy-open pattern already in the codebase): the
constructor now stores the db path only; a new `ensureOpen()` method,
called at the top of every public method, does the actual
`addDatabase`/`open`/`ensureSchema` work on first use — which, after D1's
relocation, happens on the store's *owning backend's* thread, not whichever
thread happened to call `setDbPath()` earlier.

Full suite green modulo one documented pre-existing flake
(`tst_sync_convergence`'s `remoteEditFetchesExactlyOneChangedItem`, which the
execution plan's §2 already names as flaky under `ctest -j` contention, not a
regression — confirmed passing standalone).

### 3.3 T1.4 — the backend-relocation proof (and two real bugs it caught)

New test file: `tests/calendar/tst_backend_thread_relocation.cpp` (~360
lines at this point, now longer after T1.5's additions — see §3.4). Three
cases, matching the execution plan's §3 T1.4 spec exactly:

1. **Remote, construct-then-move**: construct `RemoteCalendarBackend`
   unparented, configure it (cache dir, db path) on the "GUI" thread, move it
   to a dedicated `QThread`, then drive `loadCalendars` → `fetchItems` →
   `pushItems` → `deleteItems` from the test thread via
   `QMetaObject::invokeMethod(backend, ..., Qt::BlockingQueuedConnection)` —
   mimicking exactly how the engine calls backends. Asserts results are
   correct against a `FakeCalDavServer` fixture and that each returned
   operation's `thread()` equals the backend's thread (the v0.72
   `onOwnerThread` contract, re-verified post-move).
2. **Local, construct-then-move**: same shape against `LocalBackend`: fetch
   an empty calendar directory, `startSync` a staged creation (exercises the
   internal `AsyncFileWriter` from a relocated backend), then a
   `Sync::ChangeDetection` fingerprint round-trip
   (`collectionRevision()` → `primeRevisionCache()` →
   `cachedCollectionRevision()`) — all via the same invokeMethod pattern.
3. **Full engine run, both mapping backends relocated to the same I/O
   thread**: two `LocalBackend` instances (source/target), both moved to one
   `QThread`, registered with a real `BackendRegistry`, driven through a real
   `Kalburator::Engine::SyncEngine::runSync()`. This is the test that
   incidentally proves the "three distinct threads" invariant (execution
   plan §1.1: GUI ≠ engine-worker ≠ backend-I/O) essentially for free,
   because **`SyncEngine` already owns and internally `moveToThread()`s its
   own `SyncEngineWorker` onto a private `m_workerThread`**
   (`src/engine/syncengine.h:550-551`, `src/engine/syncengine.cpp:162-200`
   `startWorkerThread()`/`stopWorkerThread()`) — a fact this session
   discovered by reading the code, not something the execution plan called
   out explicitly. That worker thread is a genuinely separate thread from
   both the test's own thread and the relocated backends' I/O thread, with
   zero extra plumbing required in the test.

**This test caught two real, previously-undetected bugs** — not in the T1.1
patches, but in `SyncEngine` itself, and they are the direct ancestor of the
finding this whole document is about. Full detail:

`SyncEngine::prepareSyncFastPath()` (`src/engine/syncengine.cpp`, called from
`driveQueue()` — see §4.1 for exact call graph) decides, per sync mapping,
whether both sides are "unchanged" and can be skipped, by asking each
backend's `Sync::ChangeDetection` interface for a fresh revision and
comparing it against a cached one. Two spots in that function called through
the `ChangeDetection*` pointer **directly** — a bare C++ virtual call, no
`QMetaObject::invokeMethod` at all:

```cpp
// as it was, ~line 690 (pre-fix):
const QMap<QString, QString> revs = cd->collectionRevisions(ids);
...
// checkSide lambda, ~line 715 (pre-fix):
const QString stored = cd->cachedCollectionRevision(colId);
```

A third site, in `onWorkerSyncCompleted()`'s `persistRevision` lambda
(called after a mapping finishes, to persist the fresh revision for next
cycle's fast-path check), had the same pattern:

```cpp
// as it was, ~line 1140 (pre-fix):
const QString live = cd->collectionRevision(colId);
...
cd->primeRevisionCache({{colId, revision}});
```

This is **exactly** the class of bug the execution plan's viability audit
claimed didn't exist: "The engine reaches backends **only** via
`QMetaObject::invokeMethod(backend, …, Qt::BlockingQueuedConnection)`... (~19
call sites in `syncengine.cpp`)." These three call sites are a genuine,
independent 20th–22nd site the original audit missed, because they route
through a `dynamic_cast<Sync::ChangeDetection*>` pointer rather than the
`SyncBackendBase*` pointer the audit was presumably grepping for.

Pre-D1 this was harmless: `prepareSyncFastPath()` runs on whatever thread
called `SyncEngine::runSync()`, and pre-D1 that thread is always the same
thread the backend lives on (both are "the GUI thread" in production, or
"the test's own thread" in a unit test) — so a direct virtual call is
perfectly correct there. Post-D1, once a backend relocates to its own I/O
thread, that direct call becomes an honest-to-goodness cross-thread access to
a `QObject` (including its private, thread-affine `QSqlDatabase` connection)
from a foreign thread — undefined behavior by Qt's own rules, and empirically
confirmed to manifest as exactly the warning T1.2/T1.3 were written to
prevent: `QSqlDatabasePrivate::database: requested database does not belong
to the calling thread`, plus (once that warning path is hit) a
`FingerprintStore::set failed: "Driver not loaded Driver not loaded"` error
from a subsequent write attempt on the now-broken connection.

**Fix applied** (still part of commit `e15da4a`): a new file-local helper,
`runOnBackendThread()`, added to the anonymous namespace at the top of
`syncengine.cpp` (currently at line 104):

```cpp
template <typename Func>
void runOnBackendThread(QObject *backend, Func &&fn)
{
    if (QThread::currentThread() == backend->thread()) {
        fn();
    } else {
        QMetaObject::invokeMethod(backend, std::forward<Func>(fn), Qt::BlockingQueuedConnection);
    }
}
```

All three call sites now route through this helper instead of calling `cd->`
directly. **Note the same-thread branch is not a redundant optimization — it
is load-bearing correctness**, and this session initially shipped a version
of this fix *without* the same-thread check (plain unconditional
`QMetaObject::invokeMethod(..., Qt::BlockingQueuedConnection)`), which
**deadlocked** two pre-existing tests
(`tst_sync_convergence`/`tst_engine_skip_unchanged`, both ran their
sync entirely on one thread, matching the pre-D1-everywhere-else topology)
for the full 300-second ctest timeout before being caught and fixed. The
reasoning: `Qt::BlockingQueuedConnection` posts an event to the target
thread's queue and then blocks the *calling* thread waiting for it to be
processed. If calling thread == target thread, that thread is now waiting
for itself to process an event it can never get around to processing,
because it's parked waiting — a textbook self-deadlock. This is exactly why
the engine's other ~19 pre-existing call sites never needed this guard: they
are all issued from `SyncEngineWorker`'s own dedicated `m_workerThread`,
which by construction is *never* the same thread as wherever a backend lives
(pre-D1 that's the GUI thread; post-D1 it's the I/O thread) — so an
unconditional `BlockingQueuedConnection` was always safe there. The three new
sites are different in kind: they run on `SyncEngine`'s *own* thread (see
§4.1), which pre-D1 always equals the backend's thread (hence the original
code's direct calls "just worked") and only sometimes differs post-D1.

Full suite green (159/159, including both previously-deadlocking tests) after
this fix.

### 3.4 T1.5 — the GUI-stall probe (the actual Stage 1 acceptance gate)

This is where the finding this document exists to describe was uncovered.

Added `FakeCalDavServer::setResponseDelayMs(int)` (in
`tests/sync/fakecaldavserver.{h,cpp}`) — every HTTP response is deferred via
`QTimer::singleShot(ms, this, ...)` on the *server's own thread* (never a
blocking `sleep`, which would freeze the fake server's own event loop instead
of just simulating network latency — this distinction is explicitly called
out as a requirement in the execution plan's T1.5 spec).

Added a stall-probe test,
`stallProbe_relocatedBackends_stayResponsive`, to
`tst_backend_thread_relocation.cpp`, per the execution plan's T1.5
spec almost verbatim:

- `RemoteCalendarBackend` (source) syncing `TwoWay` against `LocalBackend`
  (target), both relocated to a dedicated I/O `QThread` (matching T1.4 case
  3's shape), driven through a real `SyncEngine`.
- The fake server has a 200ms per-response delay and one seeded event, so the
  sync actually has real network work to do (not a no-op skip).
- A `QTimer` on the calling ("GUI"-analog) thread ticks every 10ms while the
  sync runs; a connected lambda records `QElapsedTimer`-measured gaps between
  ticks; the test asserts the largest observed gap is under 50ms — the exact
  threshold and methodology the execution plan's T1.5 spec calls for
  ("a heartbeat proves the main thread never stalls > 50 ms through a full
  sync cycle over a latency-injected fake server").

**This test fails**, and — this is the important part — **it is not
flaky, not a test bug, and not caused by anything introduced by T1.1–T1.4**.
It measures a real, reproducible, deterministic stall of **~213ms** — almost
exactly one round-trip through the fake server's 200ms artificial delay. That
finding is the entire subject of §4 below.

An earlier version of this test also tried to assert the *inverse* — that
leaving backends un-relocated should produce a big stall, as
"RED-documentation" per the execution plan's own T1.5 spec ("Also assert the
inverse is currently true (optional but valuable RED-documentation)... This
pins that the test actually measures the freeze."). That assertion was
**dropped** after empirical testing showed it doesn't hold for this specific
harness: with a single small fetch and one backend on the calling thread, the
measured stall was only 14ms, comfortably under the 50ms threshold. The
reason, established by reading `davSyncRequest`'s implementation
(`src/calendar/remotecalendarbackend.cpp:206+`): it waits for its
`QNetworkReply` via a **nested `QEventLoop().exec()`** call, and nested event
loops in Qt continue processing *other* pending events — including unrelated
timers like our heartbeat — while they wait for their own exit condition.
So a single synchronous network call, even one sharing a thread with the
"GUI", does not manifest as a naive-heartbeat-timer stall the way this test
tried to measure it. (This is itself a small, interesting side-finding:
whatever mechanism actually produces the historical 120-second freeze in
production must be either (a) a much larger number of sequential round-trips
whose cumulative effect starves the event loop of a large-enough contiguous
window, or (b) a genuinely non-reentrant synchronous operation with **no**
internal event-loop yield point at all — `LocalBackend`'s full-directory
filesystem scan/hash for its fingerprint, which is plain unyielding C++, is a
strong candidate, though this was not verified this session.) This document
does not resolve that side-question; it's noted here so the next person
doesn't have to rediscover it. It's also documented inline in
`tst_backend_thread_relocation.cpp`'s comment above `runStallProbe()`.

Findings from this test were written up in
`docs/campaign/FINDINGS.md`, new entry **O16** (search for that exact string
— it is long and detailed; this document's §4 below is a superset of it with
more surrounding narrative). The execution plan's header and §9 checklist
were also updated to reflect "Stage 1 blocked" status.

All of the above is committed (`ec929a4`); nothing is stashed or uncommitted.
`git status` on `feature/d1-threading` is clean as of this writing.

## 4. The finding, in full technical detail

### 4.1 The exact call graph

```
SyncEngine::runSync(SyncRequest)              [src/engine/syncengine.cpp:512]
  └─ (multi-mapping path) driveQueue(...)     [src/engine/syncengine.cpp:333]
       ├─ (DecSync active controllers, if any — synchronous, unrelated)
       ├─ if (!m_queueOverride.clobber)
       │    prepareSyncFastPath()              [called at line 384]
       │      └─ for each backend implementing Sync::ChangeDetection:
       │           runOnBackendThread(base, [cd,...]{ cd->collectionRevisions(...); })   [line 724]
       │      └─ for each mapping's checkSide():
       │           runOnBackendThread(base, [cd,...]{ cd->cachedCollectionRevision(...); }) [line 753]
       ├─ startWorkerThread()                  [called at line 407, AFTER prepareSyncFastPath]
       └─ processQueue()  →  (eventually) SyncEngineWorker on m_workerThread does the real work
                                  └─ ~19 sites: QMetaObject::invokeMethod(backend, ..., BlockingQueuedConnection)
                                  └─ onWorkerSyncCompleted() [line 1123, runs on SyncEngine's own thread]
                                       └─ persistRevision lambda:
                                            runOnBackendThread(base, [cd,...]{ cd->collectionRevision(...); })  [line 1191]
                                            runOnBackendThread(base, [cd,...]{ cd->primeRevisionCache(...); }) [line 1196]
```

The critical fact, stated as plainly as possible: **`prepareSyncFastPath()`
runs synchronously, as a normal C++ function call, on whatever thread called
`runSync()` — and it runs *before* `startWorkerThread()`.** `SyncEngine`
itself is never moved to any thread (see execution plan invariant §1.2: "
`SyncEngine` and `BaselineStore` do not move"), so "whatever thread called
`runSync()`" is, in production, **the GUI thread** — `CollectionController`
(the PlanStan consumer) calls `runSync()` directly from GUI-thread code paths
(e.g. a "sync now" button handler, or a periodic timer).

`onWorkerSyncCompleted()` is a slot on `SyncEngine`; it's connected to
`SyncEngineWorker::syncCompleted` (a cross-thread signal, worker thread →
`SyncEngine`'s thread, auto-promoted to a queued connection). Since
`SyncEngine` itself is never moved, "its own thread" is, again, the GUI
thread. So this slot's body — including the `persistRevision` lambda — also
executes on the GUI thread.

### 4.2 Why the T1.4 fix (§3.3) is necessary but insufficient

The T1.4 fix made these three call sites **thread-safe**: no more
undefined-behavior cross-thread `QObject`/`QSqlDatabase` access, no more
silent SQL connection corruption, no more `Driver not loaded` errors. This
was a real, necessary fix, and it should absolutely stay.

But `Qt::BlockingQueuedConnection` — even when correctly used, even when
`runOnBackendThread()`'s same-thread guard correctly determines "yes, this is
genuinely cross-thread, marshal it" — is a **synchronous, blocking**
mechanism by design: the calling thread posts an event to the target
thread's queue and then **blocks, doing nothing else, until that event is
processed and the functor returns**. That is the whole point of
"Blocking" in the name. It does not matter which thread ends up doing the
actual network I/O; the thread that *called* `prepareSyncFastPath()` is
parked, unable to process its own event loop, for exactly as long as that
network round-trip takes.

So: pre-D1, `prepareSyncFastPath()`'s direct calls blocked the GUI thread for
the duration of a ctag/fingerprint check — call it "fast" in the common case
(one PROPFIND per backend, typically sub-100ms on a healthy connection) but
still technically synchronous I/O on the GUI thread. Post-D1, with the T1.4
fix applied, `prepareSyncFastPath()`'s **marshaled** calls block the GUI
thread for the *exact same duration* — the backend just happens to now be a
thread away instead of local, which changes nothing about how long the GUI
thread waits. **D1's backend relocation, by itself, does nothing to fix this
particular stall**, because the thing that needed to change was never "which
thread runs the network I/O" — it was "does the GUI thread wait
synchronously for it," and `prepareSyncFastPath()`'s calling convention
(`runSync()` computes fast-path eligibility synchronously, then decides
whether to `startWorkerThread()`) has always been synchronous-from-the-GUI's
perspective, D1 or no D1.

This is a fundamentally different bug shape than what T1.1–T1.4 fixed:
- T1.1–T1.3 were about **thread affinity of lazily-created resources**
  (fixable by deferring creation).
- T1.4's `prepareSyncFastPath` fix was about **thread-safety of cross-thread
  access** (fixable by marshaling).
- **This finding is about the engine's control-flow being synchronous at a
  point where, post-D1, synchronous-with-relocated-backends now means
  "synchronous over a network."** No amount of marshaling-correctness fixes
  a fundamentally synchronous call graph; only *not waiting synchronously*
  does.

### 4.3 Magnitude and scope — how bad is this, really?

Bounded, not unbounded. `prepareSyncFastPath()`'s network cost is
**O(number of `ChangeDetection`-implementing backends in the sync
mapping set) × O(one PROPFIND/fingerprint-scan round-trip each)** — not
O(number of items being synced). Both shipped backend types
(`LocalBackend`, `RemoteCalendarBackend`) implement `ChangeDetection`, so in
practice this fires on every mapping, every sync cycle, source and target
side both. On a healthy connection this is probably tens of milliseconds;
under packet loss, DNS hiccups, or a slow/overloaded server, it could be
seconds. It is **not** the multi-minute freeze N7 describes, which comes from
transferring the actual bulk item payload (hundreds of full iCal blobs) — and
that part **is** fixed by D1, proven by
`fullEngineRun_relocatedBackends_completesAcrossThreeThreads` (§3.3, case 3)
completing correctly with both backends parked on an I/O thread the whole
time, with no attempt made in that test to measure timing but with the
architecture demonstrated to be structurally sound for that phase.
`persistRevision`'s tail-end stall (§4.1, `onWorkerSyncCompleted`) is smaller
still — one round-trip *per mapping*, once, after that mapping's real work is
already done, not per-backend up front.

So: D1's actual, primary target (the bulk-transfer freeze) is fixed. This
finding is a real, separate, smaller-magnitude stall in a pre-check phase
that happens to sit in the same call graph. Whether "smaller-magnitude but
still present" is acceptable for Stage 1 to close is exactly the judgment
call this document is for.

## 5. Fix options (no recommendation made here beyond noting tradeoffs already surfaced)

These were the three options presented to the user in this session before
being asked to write this document instead of deciding live. Reproduced here
verbatim-in-spirit with the reasoning behind each:

### Option A — make `prepareSyncFastPath()` genuinely asynchronous

Restructure `driveQueue()` so `startWorkerThread()` happens *first*, and
`prepareSyncFastPath()` (plus the skip-eligibility decision it produces) runs
**on the worker thread**, dispatched via a non-blocking (`Qt::QueuedConnection`)
signal from the caller, with `runSync()`'s returned `QFuture` only completing
once the worker has finished *both* the fast-path check *and* the actual
sync. This is the architecturally "correct" fix — it makes
`prepareSyncFastPath()` follow the exact same pattern as the rest of the
sync's ~19 call sites (worker thread blocks on backend thread; GUI thread
never blocks on anything).

**Cost:** this is a real control-flow change to `driveQueue()`, which today
also handles the DecSync "active controller" loop (synchronous, runs before
the fast-path check), `m_isSyncing`/`m_cancelled` state management, and the
single-mapping vs. multi-mapping dispatch split (`processSingleMapping()`
explicitly does *not* run `prepareSyncFastPath()` at all, per a comment at
`syncengine.cpp:399` — asymmetry to be aware of). None of that is
insurmountable, but it's a genuine architecture change, not a bounded patch,
and needs its own dedicated test coverage (cancellation-during-fast-path
semantics in particular don't obviously fall out of the current design for
free). This is bigger and riskier than anything else done in Stage 1 so far.

### Option B — defer to D2, document and scope the gate narrowly

Land T1.1–T1.4 as-is (independently correct and valuable regardless of this
finding), keep O16 open, and reinterpret the T1.5 acceptance gate as covering
"the worker-thread-driven bulk phase" rather than the literal full
`runSync()`-to-`QFuture`-completion cycle. Ship v0.83 with a known, bounded,
documented residual stall, and give Option A the design attention it
deserves in a dedicated D2 task rather than rushing it into Stage 1.

**Cost:** technically ships D1 without meeting the execution plan's own
literal T1.5 wording ("never stalls > 50ms through **a full sync cycle**").
Requires an explicit, conscious decision to relax that wording (and update
the plan document to say so, not just quietly redefine "done").

### Option C — disable the fast-path skip when backends are relocated

Simplest, cheapest, no engine restructuring: gate `m_skipUnchangedMappings`
off whenever the consumer has relocated its backends (a PlanStan-side
decision, or a libkalburator flag `SyncEngine` could expose). Every sync
after that always does the real work, forgoing the "nothing changed, skip
fast" optimization — but that optimization's own *cost* was exactly this
stall, so removing it removes the stall by construction.

**Cost:** gives up a real, already-shipped performance win (see
`docs/campaign/2026-07-03-sync-convergence-roadmap.md`'s Phase B5 and the
"fast path" language throughout `FINDINGS.md` — this optimization exists
because full re-diffing every cycle was itself found to be wasteful on a
real account). Every sync becomes as expensive as a "something changed"
sync, all the time, for every relocated-backend consumer. This is very
likely an unacceptable regression for the exact kind of always-on background
sync PlanStan does every ~120 seconds — trading one performance problem for
another.
