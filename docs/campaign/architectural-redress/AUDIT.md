# Fresh-eyes audit — 2026-05-28

> **Source of truth for the architectural-redress campaign.** Generated by four parallel
> code-only audits (no docs, no comments trusted) over `src/` at commit `6579dfb`. Findings
> were cross-validated across the four agents; only items two agents found independently —
> or that one agent backed with file:line evidence the others did not contradict — survive
> into the plans.
>
> If a plan and this audit disagree, the audit wins; update the plan. If reality and this
> audit disagree, write a FINDING and update the audit in the same commit.

## TL;DR

- **The architecture is fundamentally sound.** DI everywhere, no singletons (deliberately
  deleted), per-domain plugin pattern, shape graph as the single transformation mechanism.
  The canon-upgrade campaign worked.
- **But the layering boundaries are leaking.** `types/` is no longer a types layer, `sync/`
  and the domain dirs have a circular include relationship, and there are three
  backend-adjacent dirs without a principled split.
- **Two real god classes.** `SyncEngine` (3.6 kLOC) and `RemoteCalendarBackend` (3.1 kLOC).
  The recent "unification" of `SyncEngine` + `SyncEngineWorker` is *incomplete* — they're
  still two classes in one translation unit with a back-pointer and
  `QMetaObject::invokeMethod` slot calls instead of signals.
- **Modest dead code** (~6–8 truly unreferenced interfaces). Most apparent "vestige" is
  actually deliberate scaffolding for downstream consumers; do not delete blindly.
- **Naming is mostly fine** but "Backend" is overloaded across 5 distinct concepts and
  "Canon" across at least 3.

## THE BAD — Critical / Major

### B1. `SyncEngine` god class + incomplete worker unification — **CRITICAL**

- `engine/syncengine.cpp`: **2780 LOC**; `.h`: **840 LOC**; ~25 public methods; ~20 private
  members.
- `SyncEngineWorker` is still a separate `QObject` class declared **publicly** in
  `syncengine.h` (lines ~119–335), with a back-pointer `m_engine` and is invoked via
  `QMetaObject::invokeMethod(m_engine, "onWorkerSyncCompleted", ...)` rather than signals.
- Mixed responsibilities: orchestration, worker thread mgmt, conflict handling, queue
  scheduling, baseline caching, resource lifecycle, mapping filtering.
- **Four overloads of `runSyncFuture()`** with overlapping semantics; `m_pendingOverride`
  is an implicit state machine.
- Two parallel mode enums with identical semantics
  (`SyncEngineWorker::Mode` vs `SyncEngine::SyncBehavior`).

### B2. `types/` is not a types layer — **CRITICAL**

- `types/logicalcalendar.h` (658 LOC): JSON ser/deser, validation, binding-promotion logic.
- `types/calendarmetadatamanager.cpp`: atomic file writes (VDir spec).
- `types/crashjournal.cpp`: JSON crash-recovery persistence.
- `types/backendconfiguration.cpp`: 200+ LOC JSON.
- `types/incidencelock_registry.cpp`: lock state mgmt.
- `types/iincidenceregistry.h` directly includes `<KCalendarCore/Incidence>` and
  `<KCalendarCore/MemoryCalendar>` — a calendar-domain interface masquerading as a neutral
  type. Pulls KCalendarCore into every consumer of `types/`.
- `types/logicalcalendar.h` and `iincidenceregistry.h` `#include "shape.h"` — the lowest
  layer depending upward.

### B3. `RemoteCalendarBackend` god class — **MAJOR**

- 2649 LOC `.cpp`, 427 LOC `.h`, **~58 public methods** spanning 7 concerns: CTag mgmt,
  discovery cache, calendar CRUD, incidence ops, raw ICS access, IBlobBackend impl,
  ChangeDetection capability.
- `ChangeDetection::collectionRevision(id)` is a trivial delegate to `ctag(id)` — same
  data, two APIs.
- Six separate `discoveredX(id)` getters for what should be one DTO.
- Same pattern in `LocalBackend` (1300 LOC, ~35 public methods, 4 separate metadata
  setters).

### B4. Circular dependency `sync/ ↔ calendar/` and `sync/ ↔ contacts/` — **CRITICAL**

- `sync/akonadiprovider.cpp` `#include "../calendar/akonadibackend.h"` to instantiate it
  directly.
- `sync/akonadibackendcontribution.cpp` `#include "../contacts/akonadicontactsbackend.h"`.
- `calendar/akonadibackend.h` `#include "syncoperation.h"` (from sync/) — the cycle closes.
- `SyncBackend` base class lives in `calendar/syncbackend.h` (319 LOC), but
  `sync/syncbackendbase.h` already exists as the neutral base. So calendar/ has its own
  competing base that sync/ consumes — inverted ownership.

### B5. Three backend-adjacent dirs without principle — **MAJOR**

- `backend/`: 1 file (`changedetection.h`).
- `storage/`: `baselinestore`, `idmappingstore`.
- `universal/`: `genericsqlitebackend`, `rawfilesbackend`, `markdownfilesbackend`,
  `filteredcollectionbackend`.
- No clear ownership. `changedetection.h` is a capability, not a backend; `storage/` is
  persistence; `universal/` is concrete generic backends.

### B6. `shape/` is not purely domain-neutral — **MAJOR**

- `shape/recordwriter.h` includes `backendrecord.h` (a `types/` concrete record type) —
  couples the abstract transformation layer to a concrete domain DTO.
- `shape/recordmerger.h` and `shape/canonjsonmerger.h` include `conflict/conflictpolicy.h`.

## THE BAD — Moderate

### B7. `CalendarManager` — **MODERATE**

- 927 LOC, ~25 public methods, mixes Calendar CRUD + Binding CRUD + Incidence CRUD + bulk.
- `DeleteMode { Hide, Disable, Forget, DeleteFromAll }` enum hides four very different
  operations behind one method.
- Same procedural skeleton (resolve backends → check capabilities → call → regenerate
  mapping → update baseline → persist config) duplicated across methods.

### B8. `IncidenceDiff` — **MODERATE**

- 1160 LOC, 20+ static methods. A namespace masquerading as a class.
- Equivalent in `vcarddiffer`, `icalvtododiffer`.

### B9. Dead/unused interfaces — **MINOR**

Candidates with 0–1 external references (including tests):

- `src/types/icommanddispatcher.h`
- `src/types/iincidencesource.h`
- `src/types/incidenceref.h`
- `src/calendar/incidencesyncadapter.h`
- `src/backend/resourcelinearization.h`
- `src/calendar/iconflictpresenter.h`
- 5 signals in `mockblobbackend.h` / `localblobbackend.h` (`recordCreated`, `recordUpdated`,

**Caveat:** confirm no out-of-tree consumer (PlanStan, WildPalms) imports these. The
`[[deprecated]]` v2 baseline APIs are intentional migration scaffolding for downstream;
don't lump them in here.

## THE UGLY — Naming & Semantics

### U1. "Backend" overloaded — **HIGH confusion**

Same word means: abstract sync interface (`SyncBackend`), abstract blob interface
(`IBlobBackend`), registration object (`BackendContribution`), config struct
(`BackendConfiguration`), capability set (`BackendCapabilities`), capability mixin
(`ChangeDetection`).

### U2. "Canon" overloaded — **MEDIUM**

`CanonEnvelope`, `CanonicalRecord`, `*CanonStages`, `canonicalShape()`, `*CanonProperties`
— three or four distinct meanings (the canonical encoding, the spine vertex, the property
catalogue, the staging pipeline).

### U3. "Store" / "Registry" / "Manager" inconsistent

- Some "stores" persist to disk (`BaselineStore`), some are in-memory maps (`ConflictStore`).
- "Manager" (`CalendarManager`, `CalendarMetadataManager`) does different things.
- `CalendarMetadataManager` lives in `types/` despite being calendar-specific file I/O.

### U4. `BackendRegistry` has two roles

Holds both live backend instances **and** factory contributions. Caller can't tell from a
method name which kind they get.

### U5. Misleading method names

- `RemoteCalendarBackend::collectionRevision(id)` — sounds like a fetch; it's an in-memory
  cache read identical to `ctag(id)`.
- `CalendarManager::updateLogicalCalendar()` — sounds like in-memory mutation; persists to
  disk.
- `storeCalendars(...)` / `loadCalendars(...)` — plural but per-collection.
- `isValid()` — context-dependent meaning across 20+ classes.

## What not to touch

- The DI / no-singleton discipline. Load-bearing decision.
- The per-domain plugin symmetry. The duplication is principled; collapsing it would
  obscure where domain knowledge actually lives.
- The shape graph as sole transformation mechanism. The `transcoding/` collapse was the
  right call and held.
- The `[[deprecated]]` baseline v2 surface. It's intentional migration scaffolding.
